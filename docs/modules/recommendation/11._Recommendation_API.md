API-CONTRACT-008 — Recommendation API

Version historique : V1  
Statut historique : MVP (non vérifié ; ne signifie pas déployé)

1. Mission

La Recommendation API expose les recommandations personnalisées produites par le Recommendation Engine. Son objectif est d'aider chaque utilisateur dans sa prise de décision. Elle ne remplace jamais le choix de l'utilisateur.

2. Position dans l'architecture

Interface → Recommendation API → Recommendation Domain → Recommendation Engine → Database.

Le Recommendation Engine agrège des informations provenant de plusieurs domaines afin de produire des recommandations personnalisées.

3. Responsabilités

La Recommendation API expose les recommandations, permet leur consultation et enregistre les réactions de l'utilisateur. Elle ne crée pas directement les recommandations : celles-ci sont produites par le moteur.

4. Capacités

- consulter ses recommandations ;
- consulter une recommandation détaillée ;
- enregistrer une recommandation ;
- masquer une recommandation ;
- indiquer qu'une recommandation a été suivie ;
- signaler une recommandation non pertinente.

5. Objet métier historique

Une Recommendation représente une action personnalisée proposée à un utilisateur. Elle peut concerner une mission, un Flash, une opportunité détectée, une personne, une compétence, un contenu ou une action à réaliser. Le document historique mentionnait un score de pertinence, une priorité, une justification et une période de validité. **Le score n'est pas retenu dans le contrat V1 actuel** ; voir [API_AND_DATA_CONTRACT.md](API_AND_DATA_CONTRACT.md).

6. Règles métier historiques

- les recommandations sont produites par le Recommendation Engine ;
- elles sont personnalisées pour chaque utilisateur ;
- elles doivent pouvoir être justifiées ;
- elles respectent les paramètres de confidentialité.

Le document historique indiquait que les réactions amélioreraient progressivement les modèles. Cette réutilisation n'est pas automatique : elle est soumise à une politique transparente, à une finalité autorisée et aux règles de gouvernance définies dans la documentation V1.

7. Contrat REST proposé historiquement

- GET /recommendations
- GET /recommendations/{id}
- POST /recommendations/{id}/save
- POST /recommendations/{id}/dismiss
- POST /recommendations/{id}/accept
- POST /recommendations/{id}/report

Ces routes sont des propositions documentaires, non des endpoints actifs confirmés.

8. Validation et sécurité attendues

L'API devra vérifier les droits d'accès, la disponibilité de la recommandation, la cohérence de l'action demandée et la période de validité. Toutes les opérations personnelles nécessitent une authentification et une isolation stricte par destinataire. La permission sur la ressource source doit être revérifiée.

9. Dépendances et domaines sources historiques

Le document historique citait Auth API et Unified Digital Identity API comme dépendances, et Trust, Radar, Veille, Flash et Mission comme domaines sources potentiels. Chaque domaine reste propriétaire de ses données. Cette liste ne signifie pas que les connecteurs sont disponibles ou autorisés aujourd'hui.

10. Événements historiques

- RecommendationViewed
- RecommendationAccepted
- RecommendationDismissed
- RecommendationSaved
- RecommendationReported

L'enveloppe, la livraison, l'idempotence, la rétention et les consommateurs de ces événements restent à spécifier avant implémentation.

11. Évolutions futures envisagées historiquement

Le document initial évoquait des modèles d'IA avancés, recommandations prédictives ou collaboratives, assistants intelligents et recommandations multimodales. Ces éléments ne font pas partie des capacités V1 promises.
