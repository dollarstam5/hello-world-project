# API-CONTRACT-002 — Unified Digital Identity API

(Profile API)

Version : V1  
Statut : contrat historique enrichi — les routes et intégrations restent à vérifier contre le runtime.

## 1. Mission

La Unified Digital Identity API (UDI API), présentée dans l'interface sous le nom **Profil**, expose une représentation unifiée de l'identité numérique de l'utilisateur.

Elle constitue le point d'accès transversal permettant aux interfaces autorisées de consulter et de mettre à jour les informations d'identité dont l'utilisateur est propriétaire. Elle agrège les vues produites par les domaines métier, sans calculer leurs données ni devenir propriétaire de celles-ci.

L'UDI API ne constitue pas une autorisation générale d'exposer l'intégralité du profil à tous les moteurs ou à tous les utilisateurs.

## 2. Position dans l'architecture

Cette API appartient à la couche des API Contracts. Elle dialogue avec la couche d'agrégation UDI, qui construit une représentation de l'identité à partir des domaines métier.

Chaîne de responsabilité :

`Interface → UDI API → Unified Digital Identity (agrégation et projection) → Business Domains`

Chaque domaine producteur reste responsable de ses données et de ses règles métier. L'UDI ne contourne pas les autorisations des domaines.

## 3. Responsabilités

L'UDI API est responsable de :

- exposer une représentation cohérente de l'identité numérique ;
- permettre la mise à jour des informations dont l'utilisateur est propriétaire et qui sont modifiables ;
- exposer les différentes vues produites par les domaines ;
- garantir que les champs retournés sont autorisés dans le contexte de consultation.

Elle ne modifie jamais directement les données propriétaires de Trust, Recommendation, Radar, Veille, Flash, Mission ou d'un autre domaine. Ces informations proviennent exclusivement des domaines concernés.

## 4. Capacités historiques

Le contrat historique prévoit notamment :

- consulter son identité numérique ;
- modifier les informations d'identité ;
- gérer les compétences ;
- gérer les intentions ;
- gérer les préférences ;
- gérer les paramètres de confidentialité ;
- consulter les vues Trust, Activity, Radar, Veille, Recommendation et Statistics.

Ces capacités sont des éléments du contrat cible. Leur disponibilité effective doit être vérifiée séparément dans les API et le runtime.

## 5. Modules exposés

L'identité numérique peut présenter les modules suivants :

- **Identity** : identifiant, nom, photo, langue, pays, vérifications et statut du compte ;
- **Capabilities** : compétences, expertises, expériences, certifications et centres d'intérêt ;
- **Context** : localisation, disponibilité, mobilité et fuseau horaire ;
- **Intentions** : objectifs dynamiques de l'utilisateur ;
- **Preferences** : préférences produites par Radar, Veille, Recommendation et les autres domaines concernés ;
- **Privacy** : règles de visibilité, consentements et préférences de confidentialité ;
- **Activity View** : Flash publiés, réponses, missions, interactions et historique ;
- **Trust View** : informations exposées par le Trust Engine ;
- **Recommendation View** : recommandations produites par Recommendation ;
- **Radar View** : informations produites par Radar ;
- **Veille View** : informations produites par Veille ;
- **Statistics** : indicateurs agrégés produits par les domaines responsables.

Chaque module reste alimenté par son domaine métier propriétaire.

## 6. Projections de profil et autorisations

Une vue unifiée n'implique pas que tous ses champs soient visibles dans tous les contextes.

- Chaque moteur demande une projection adaptée à son propre usage.
- Une permission donnée dans un moteur n'est jamais héritée automatiquement par un autre.
- Les réglages propres à une publication ou à une action s'appliquent à ce contexte sans élargir les autorisations générales du profil.
- L'accès au profil complet est une autorisation distincte, explicite et propre au moteur lorsque le produit le prévoit.
- Les champs non autorisés doivent être exclus de la réponse API ; les masquer uniquement dans l'interface est insuffisant.
- Les règles doivent couvrir les utilisateurs membres, les invités et les accès hors périmètre.
- Une révocation de consentement doit être respectée lors des consultations suivantes et par les mécanismes de cache concernés.

Les règles détaillées sont définies dans [la politique de visibilité par moteur](../03-engines/visibility-and-profile-policy.md) et dans les fiches de chaque moteur. L'UDI fournit les données autorisées ; le moteur consommateur reste responsable de son contrat métier.

## 7. Contrat REST historique

Les routes historiques de référence sont :

- `GET /me`
- `PATCH /me/identity`
- `PATCH /me/capabilities`
- `PATCH /me/context`
- `PATCH /me/intentions`
- `PATCH /me/preferences`
- `PATCH /me/privacy`
- `GET /me/activity`
- `GET /me/trust`
- `GET /me/radar`
- `GET /me/veille`
- `GET /me/recommendations`
- `GET /me/statistics`

Toutes les réponses doivent suivre le format standard des API Vitalis. Les chemins exacts, schémas de réponse, paramètres de projection, codes d'erreur et contrôles d'accès doivent être confirmés contre les contrats et le runtime actuels avant de présenter ces routes comme disponibles.

## 8. Validation

Le contrat prévoit notamment la validation :

- des champs modifiables par l'utilisateur ;
- des formats de données ;
- des droits d'accès ;
- de la cohérence des mises à jour.

Les données produites par les moteurs ne peuvent pas être modifiées via l'UDI API.

La validation future doit aussi vérifier les projections autorisées, les refus d'accès, les utilisateurs membres et invités, les accès inter-comptes et l'absence de champs privés dans les réponses réseau.

## 9. Sécurité

L'accès aux opérations personnelles est soumis à l'authentification et aux autorisations applicables.

Chaque opération est soumise :

- à l'authentification ;
- aux autorisations ;
- aux règles de confidentialité ;
- à la journalisation des actions importantes.

Les règles de visibilité doivent être appliquées côté serveur et dans les politiques d'accès des domaines propriétaires. Une protection uniquement visuelle n'est pas suffisante.

## 10. Dépendances historiques

Le contrat historique mentionne :

- Auth API ;
- Trust API ;
- Flash API ;
- Mission API ;
- Radar API ;
- Veille API ;
- Recommendation API ;
- Settings API ;
- Media.

L'UDI ne remplace aucun de ces domaines ; elle agrège leurs vues autorisées. La disponibilité et le raccordement de chaque dépendance doivent être vérifiés séparément.

## 11. Événements historiques

Les mises à jour autorisées peuvent produire des événements tels que :

- `IdentityUpdated`
- `CapabilitiesUpdated`
- `IntentionsUpdated`
- `PreferencesUpdated`
- `PrivacyUpdated`

Le contrat historique indique que les vues évoluent lorsque leurs domaines producteurs changent. Les noms exacts, les producteurs, les consommateurs et l'émission effective de ces événements doivent être confirmés dans les contrats actuels et le runtime.

## 12. Évolutions futures

L'architecture permet d'ajouter de nouveaux modules, par exemple Organization Identity, Project Identity ou Community Identity, sans transformer l'UDI en propriétaire des données métier.

Toute extension doit préserver la séparation entre propriété des données, agrégation et autorisation de visibilité.
