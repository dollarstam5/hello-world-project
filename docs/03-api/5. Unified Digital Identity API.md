# API-CONTRACT-002 — Unified Digital Identity API

Version : V1  
Statut documentaire : contrat historique à aligner avec les implémentations vérifiées.

## 1. Mission

La Unified Digital Identity API (UDI API), présentée à l'utilisateur sous le nom **Profil**, expose une représentation unifiée de l'identité numérique. Elle agrège les vues produites par les domaines métier et permet de consulter ou modifier uniquement les éléments dont l'utilisateur est propriétaire et pour lesquels l'opération est autorisée.

L'UDI API ne calcule aucune donnée métier et ne devient pas propriétaire des données produites par les autres domaines.

## 2. Position dans l'architecture

Chaîne de responsabilité cible :

`Interface → UDI API → UDI (agrégation et projection) → domaines métier propriétaires`

L'UDI construit une représentation contrôlée à partir des contrats des domaines producteurs. Elle ne contourne pas leurs règles d'accès.

## 3. Responsabilités

L'API est responsable de :

- exposer une représentation cohérente de l'identité ;
- permettre la mise à jour des seules informations modifiables par l'utilisateur ;
- présenter les vues fournies par les domaines ;
- appliquer les règles d'accès et de visibilité au contexte de consultation.

Elle ne modifie jamais directement les données de Trust, Recommendation, Radar, Veille, Flash, Mission ou d'un autre domaine propriétaire.

## 4. Modules représentés

Les vues peuvent comprendre Identity, Capabilities, Context, Intentions, Preferences, Privacy, Activity, Trust, Recommendation, Radar, Veille et Statistics. Chaque vue reste alimentée par son domaine métier propriétaire.

## 5. Projections et autorisations

Une réponse UDI n'implique pas que tous les champs soient accessibles dans tous les contextes.

- Les interfaces et moteurs demandent une projection adaptée à leur usage.
- Les champs exposés sont limités aux autorisations du contexte et aux règles du domaine propriétaire.
- Une permission accordée dans un moteur ne vaut pas permission dans un autre.
- L'accès au profil complet est distinct et exige un consentement explicite lorsque le produit le prévoit.
- Les champs non autorisés sont exclus de la réponse API ; les masquer uniquement côté interface est insuffisant.
- Les règles d'accès s'appliquent également aux utilisateurs invités et aux consultations hors périmètre.

Les contrats propres aux domaines restent responsables des autorisations métier détaillées. L'UDI API ne doit pas élargir ces autorisations.

## 6. Contrats REST historiques

Les routes suivantes figurent dans le contrat historique et doivent être considérées comme des références à vérifier contre le runtime avant d'être présentées comme disponibles :

- `GET /me`
- `PATCH /me/identity`
- `PATCH /me/capabilities`
- `PATCH /me/context`
- `PATCH /me/intentions`
- `PATCH /me/preferences`
- `PATCH /me/privacy`
- `GET /me/activity`
- `GET /me/trust`
- `GET /me/radar`
- `GET /me/veille`
- `GET /me/recommendations`
- `GET /me/statistics`

Les chemins exacts, schémas de réponse, projections et contrôles d'accès doivent être confirmés par les contrats API et les tests du runtime.

## 7. Sécurité et gouvernance

Toutes les opérations sont soumises à l'authentification, aux autorisations, aux règles de confidentialité et à la journalisation des actions importantes. Les données produites par un moteur ne peuvent pas être modifiées par l'UDI API.

Chaque domaine reste la source de vérité de ses données. Les vues UDI ne doivent ni dupliquer les données ni exposer des champs non autorisés.

## 8. Dépendances

Les dépendances historiques comprennent notamment Auth, Profile, Trust, Flash, Mission, Radar, Veille, Recommendation, Settings et Media. Leur disponibilité et leur raccordement doivent être vérifiés séparément.

## 9. Événements

Les événements historiques comprennent IdentityUpdated, CapabilitiesUpdated, IntentionsUpdated, PreferencesUpdated et PrivacyUpdated. Les événements exacts et leur émission effective doivent être confirmés dans les contrats et le runtime.

## 10. Statut et validation

Ce document conserve les responsabilités métier et la structure de l'ancien contrat, tout en précisant la séparation entre agrégation et autorisation. Il ne certifie pas que toutes les routes ou vues historiques sont actuellement déployées.

La validation exige notamment des tests de propriété des données, de projection par moteur, de refus d'accès, de séparation membre/invité et d'absence de champs privés dans les réponses réseau.
